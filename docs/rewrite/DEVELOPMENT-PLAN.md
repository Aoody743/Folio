更新：2026-10-13（Asia/Singapore）。本文件为当前执行计划，取代早期多阶段重写草案。

当前按三个阶段实施。第一阶段基础工程、静态界面、认证、共享便签、任务、原生 MCP、发行包及真实 Debian 虚拟机闭环已通过验收，见[验收记录](PHASE1-ACCEPTANCE.md)。第二阶段正在实现核心管理及 23 个插件，第三阶段尚未开始；实际结果与未执行项以验收记录为准，计划不代表检查已通过。

用户最新要求恢复云端开发，使用 GPT-6 Luna max 按小批次完成第二阶段。首批已打通 ACME `SubmitPrepared`/order receipt、Core FULL 与 secret fsync/有界 enqueue retry、Sites durable WAL/identity/SIGKILL 检查，以及数据库 deleted CAS/receipt code、状态 UI 和备份下载。检查结果与证据链接见[进度记录](PROGRESS.md#当前执行状态优先于历史交接与下方旧批次)。

历史交接安排（保留）：上一轮要求先将当时完整源码推送至 `refine`，再由本地 Codex 继续。该记录不再代表当前工作优先级；当前执行以本节云端完成第二阶段的要求为准。接续背景仍见 [HANDOFF](HANDOFF.md)。

## 最终目标与固定约束

- 全新重构，前端 Next.js + React 19 + TypeScript + Astryx，Go后端与独立Agent，SQLite持久化。
- 前端优先静态导出，由Go提供界面与API，核心安装不依赖常驻Node/Python或本地大模型。
- 精简信息面板，底部五项导航，四卡首页，五套配色，桌面/移动适配。
- 人与外部AI通过MCP共同读写共享便签，有真实身份、版本、历史和冲突处理；面板不内置聊天或模型界面。
- 原生MCP从第一阶段开发，与网页/REST共用动作、权限、任务和审计，支持stdio与Streamable HTTP。
- 现有全部有效功能和70个插件均进入迁移范围；低侵入通过受控、按需系统变更实现。
- Linux预编译发行包、一键安装、可验证升级/迁移/恢复和卸载；开发、CI及宿主验收全程云端完成。

1. 从干净云端开发环境可以重复安装依赖、构建并启动，不依靠未记录的手工步骤。
2. 前端静态产物由Go提供；普通用户运行API，初始化/登录/MFA/会话撤销及权限拒绝均有真实断言。
3. 四卡首页读取真实状态；五个主题、桌面/手机与键盘交互通过。更深入功能入口明确显示开发状态。
4. 人新建便签 → MCP客户端读取 → AI修改 → 网页更新 → 查看历史，整个链路成功；并发冲突、断线、失败均不丢草稿。
5. 目标MCP客户端完成两种传输的协商、工具发现和调用；未授权调用被拒绝，Token撤销有效。
6. 至少一个持久化写任务有真实成功/失败/取消与结果验证；大量输出和超时不会卡住或遗留不可管理进程。
7. 核心预编译安装包至少在一台干净云VM验证安装、启动、重复运行安装脚本及健康检查。
8. 形成第一份可重复的延迟、内存、首屏资源和系统变更基线。

达到本阶段只能称基础可用，不能宣称网站、数据库或全部插件已完成。

`openresty`、`php`、`php-apt`、`php-yum`、`php-guard`、`phpmyadmin`、`mysql`、`mysql-community`、`mariadb`、`postgresql`、`mongodb`、`pgadmin`、`data_query`、`redis`、`valkey`、`memcached`、`docker`、`pureftp`、`rsyncd`、`backup_ftp`、`acme_pandominassl_apply`、`supervisor`、`webssh`。

### 退出标准

1. 核心运维闭环：安装Web/PHP → 建站 → 绑定域名/TLS → 创建数据库 → 上传文件 → 验证访问 → 备份 → 在临时目标恢复。
2. 文件、终端、Docker、计划任务、安全与设置覆盖已登记的用户行为及错误场景。
3. 23个插件的有效动作、受支持版本/平台、特有功能均有验收记录；旧声明不可用时记录原因，不能直接假装已迁移。
4. 同一操作经网页与MCP执行时有一致的权限、任务、结果与审计；并发修改/网络重试不会重复或覆盖资源。
5. SSH、防火墙与服务配置变更具有预检、连接保护、备份/恢复；普通查询不触发修改系统。
6. 同一机器上旧管理器和新管理器不能同时修改相同资源；迁移前的引用与归属可追踪。
7. 核心功能经过容器与真实云VM的适用检查，未执行项如实标记；测试版安装/重复安装及基本升级通过。

## 云端开发与测试安排

日常工作区用于代码、UI、契约、SQLite与受控文件测试；临时容器用于软件/数据库集成；可丢弃云VM用于systemd、权限、网络、防火墙与安装/升级/迁移验收。

开发阶段不得在共享宿主直接运行旧版全局安装器。数据/权限模拟只能验证对应逻辑，不能证明真实Linux宿主行为已通过。

VM和第三方DNS/云盘/邮件/其他服务的测试访问在用到时，通过环境安全配置提供；文档和Git不保存凭据。缺少前提时继续无依赖工作并记录阻塞，不用mock结果替代真实外部检查。

PR/main的检查按阶段逐步增加：构建与类型/契约 → 认证/便签/MCP/任务回归 → 核心服务集成 → 全量插件、迁移、宿主、性能和发行。阶段退出时相关检查必须完整执行。

## 性能与系统修改预算

第一阶段测量并记录基线，在第二阶段前固定测试条件；第三阶段以相同条件比较。初始目标：

- 基准主机2 vCPU/2GiB，固定OS、架构、数据规模、并发和采样频率。
- 20并发下缓存型只读API服务端HTTP p95 <100ms；长任务提交与真实完成耗时分别统计。
- 面板API与必要Agent空闲RSS总量初始目标≤100MiB，不包括第三方服务、模型和前端开发工具。
- 首屏优先加载导航、首页和便签；终端/编辑器/大图表按需。第一阶段依据真实构建冻结资源预算。
- 核心安装只修改自有用户、目录与服务；不替换系统Shell、不默认修改locale/motd/防火墙/root cron。显式管理动作产生的系统变更有归属、记录和恢复策略。

这些是待测目标，不是已经达到的结果。如基线暴露结构问题，应解决并重新验证，不仅调整文档数字使结果看起来通过。

## 工作节奏与时间估算

每次开发以一个可验收闭环为单位，交付代码、对应验证和台账更新；阶段末给出通过项、失败项、阻塞及下一阶段依赖。

不在尚无新版工程、未完成首个服务适配时承诺准确日历工期。第一阶段完成基础闭环后，按实际速度、插件动作/版本复杂度和外部验收条件估算后两阶段。第三阶段的47个插件与兼容验收是实质开发工作，不能当作短暂收尾。

当前按用户要求在云端用 GPT-6 Luna max 逐步完成第二阶段；每个批次更新实现、验证和证据，再继续剩余范围。阶段退出前保持失败、阻塞和未执行项可见，不以构建或源测试替代发行版及外部服务验收。此前关于交付 `refine` 和本地接续的内容作为历史背景保留。
