# Folio rewrite build and installation

Upcoming beta4 installer and bilingual UI: [experience notes](../../docs/rewrite/EXPERIENCE-BETA4.md). Use `--lang zh-CN|en` and `--yes` for unattended installation. Earlier versioned bootstrap scripts remain unchanged.

These scripts operate the new Go/Next.js runtime. They never invoke the legacy
Python panel, its installers, or its update URLs. Run in the existing isolated
checkout; do not create an extra Git worktree for normal cloud tasks.

## Development

Use the exact Go version in `go.mod`, Node.js 24 LTS and npm. The committed
`frontend/package-lock.json` is installed with `npm ci`; no mutable dependency
resolution is performed during build. Go uses `-mod=readonly` for release builds.
Build caches and development data are under `.cache/rewrite` (ignored by Git).

```sh
make rewrite-deps
make rewrite-test
make rewrite-build REWRITE_VERSION=0.1.0-dev.1
make rewrite-dev
```

`GO_BIN=/absolute/path/to/go` selects an existing pinned compiler. `REWRITE_CACHE`
changes caches, `REWRITE_OUTPUT` changes the package directory and
`REWRITE_ARCHITECTURES=amd64` builds one target. `POWERLINUX_DATA_DIR` and
`POWERLINUX_LISTEN` configure the development server. Backend bootstrap credentials
are generated by the server into its protected data directory; never embed them
in scripts or commit them. Development server readiness means an actual `/healthz`
request and authenticated workflow work, not only a PID. Development/prefix
commands explicitly use `--server-config ''` to avoid inheriting another
production instance's root-owned port, TLS or public URL configuration. This
does not relax the loopback HTTP and certificate-validation requirements.
Builds use two concurrent Go packages by default; `POWERLINUX_BUILD_PARALLELISM`
can be set from 1 to 32 for the cloud machine's CPU/memory budget.
After a successful frozen dependency install, `REWRITE_BUILD_FLAGS=--skip-install`
avoids installing npm dependencies a second time while retaining typecheck and
frontend build. The default build is self-contained and always runs `npm ci`.
`build.sh --skip-frontend` is for an already validated coherent `frontend/out`;
it skips both frontend installation and compilation. Concurrent release builds
are excluded by a checkout-local lock while they refresh/use embedded assets.

`build.sh` constructs the Next static export, copies it into
`internal/webassets/dist`, and compiles CGO-free Linux amd64/arm64 binaries with
embedded assets. Each package exposes the `folio` command and includes a
byte-identical `powerlinux` executable for existing service and upgrade paths.
Archives are named `folio-VERSION-linux-ARCH.tar.gz`. Packages include a version, platform, source commit and Go
compiler record, plus an explicit working-tree-dirty flag so an uncommitted
development build is not represented as the exact commit's code. Deterministic tar timestamps come from `SOURCE_DATE_EPOCH` or
the current commit. Build output reproducibility is separate from source
provenance and host compatibility. User servers need no Node, Go or Python.

## Verified installation

For the 1.0-beta2 Linux amd64 release, the release includes a one-command
bootstrap installer. On a fresh Ubuntu 24.04 amd64 systemd host, run:

```sh
curl -fsSL https://github.com/Aoody743/Folio/releases/download/1.0-beta2/install-1.0-beta2.sh | sudo bash
```

The bootstrap downloads the beta2 archive and release `SHA256SUMS.txt`, checks
the package SHA-256, then passes that archive to the package installer. A fresh
system install enables the reviewed software and website/certificate modules;
upgrades preserve an existing Agent policy. Use `--no-managed-features` to skip
the default module setup. `--prefix` creates no system user or service. The
one-command bootstrap targets Linux amd64; the selected runtime catalog was
accepted only on Ubuntu 24.04 amd64.

Download and review `install.sh` from a trusted project revision. Obtain the
artifact hash from a trusted release record before running the installer.

```sh
bash scripts/rewrite/install.sh --archive /path/to/folio-VERSION-linux-amd64.tar.gz \
  --sha256 SHA256_FROM_TRUSTED_RELEASE --prefix /absolute/path/to/powerlinux-test
```

For systemd hosts, omit `--prefix` and run the reviewed script as root. A remote
release can use `--version VERSION --sha256 TRUSTED_HASH`; only project GitHub
HTTPS release URLs are fetched and TLS checking stays enabled. New release
archives contain exactly seven regular, flat members. Six-member legacy RC
archives remain accepted and are normalized to include the `folio` command.
Links, unknown files, traversal, duplicate members, wrong platforms and
hash/version mismatches are rejected before installing either executable. A GitHub-published build attestation can be
verified with `--attestation` when a GitHub CLI supporting attestations is present.
The expected signer workflow is `.github/workflows/rewrite-ci.yml` in this repo.
CI uploads development packages and provenance; it does not publish a release.
Public release signing/provenance policy must be validated before a stable release.

An SHA256 obtained through the same channel detects corruption and mismatch;
it does not independently authenticate a compromised publisher. Protect the pin
and verify provenance when operating untrusted download/storage channels.

Production paths are `/opt/powerlinux` (versioned binaries/backups),
`/var/lib/powerlinux` (database/data), `/etc/powerlinux` (owned configuration) and
`/etc/systemd/system/powerlinux.service`. An ordinary noninteractive `powerlinux`
system user runs the API with systemd hardening. The installer refuses existing
unmanaged locations or an unrelated user/unit. It changes no system shell,
locale, firewall, motd or root cron. Third-party service installation is optional
application behavior, never a core installer side effect.

The service binds `127.0.0.1:9000` by default. The production unit reads preserved
root-owned `/etc/powerlinux/server.json`; it does not override the configured
listen address. The config directory is root:powerlinux 0750 and the server
document root:powerlinux 0640. Use an SSH tunnel or an explicitly configured
verified HTTPS endpoint. There is no default public exposure or administrator
password. Deployment health checks use the executable's typed config/TLS parser,
check ready and exact version, verify certificates and reject redirects.

After installation, inspect `systemctl status powerlinux.service` and run the
typed health check against the preserved production configuration:

```sh
/opt/powerlinux/current/folio healthcheck \
  --server-config /etc/powerlinux/server.json \
  --expected-version VERSION_FROM_TRUSTED_RELEASE --timeout 3s
ssh -L 9000:127.0.0.1:9000 your-user@your-server
```

Open `http://127.0.0.1:9000` through this tunnel. For an uninitialized instance,
obtain the private `/var/lib/powerlinux/bootstrap-token` from the server's local
administrator console and use the initial setup form to choose administrator
credentials. The token is removed after setup and is not written to service
logs. Keep the browser's origin consistent with the configured allowed origins;
an alternative forwarded port requires its exact origin in the reviewed server
configuration. Do not put credentials in URL query strings or shell arguments.

## Optional privileged host executor

The API stays an ordinary user. The optional host executor is enabled only by a
reviewed root-only policy; it is a typed operating-system dispatcher, not an AI
agent and not a model runtime. Absent typed modules remain disabled. Review
[`examples/agent-policy-v2.json`](examples/agent-policy-v2.json), adapt known local
program paths, and install a private copy outside the API-owned data directory.
The example enables only the panel service/configuration, isolated scripts and
isolated terminal. It enables no root shell, SSH/firewall changes, software
installation or global package manager.

```sh
install -m 0600 -o root -g root scripts/rewrite/examples/agent-policy-v2.json /root/powerlinux-policy.json
bash scripts/rewrite/install.sh --archive /path/to/actual-new-package.tar.gz \
  --sha256 TRUSTED_RELEASE_HASH --enable-agent \
  --agent-policy /root/powerlinux-policy.json --enable-terminal
```

`--enable-terminal` creates a separate noninteractive `powerlinux-terminal` user,
private `/var/lib/powerlinux-terminal` home and workspace. The trusted Agent
launches its explicit shell after dropping supplementary groups and inherited
environment. The shell's UID cannot read the API database or encryption key.
`--enable-software` creates a separate `powerlinux-services` user and owned
`/opt/powerlinux-software`; `--enable-sites` prepares `/srv/powerlinux-sites`.
These flags prepare module dependencies; the explicit policy determines which
modules/actions can run. Additional users/dirs persist after rollback/uninstall.

Separate templates keep opt-in authority explicit:
[`agent-policy-files-readonly.json`](examples/agent-policy-files-readonly.json)
exposes only an operator-selected `/srv/powerlinux-files` directory for reading.
Create that dedicated directory as root before checking this policy; the
installer does not create arbitrary file roots or enable host-wide access.
[`agent-policy-software-sites.json`](examples/agent-policy-software-sites.json)
enables receipt-backed software, sites and hosted applications with
`--enable-software --enable-sites`. This reviewed policy also allows software
plans to install packages from the host's signature-verified distribution
repositories, including the native Nginx package selected during first-run
setup. It does not enable a terminal, host configuration or full-host files.
Website runtimes must still be installed through explicit software plans.
The software module also creates the protected `/srv/powerlinux-apps` data root
for hosted Next.js and Go projects; `applications_root_dir` in the reviewed
policy must point to that path. This root is preserved on rollback and
uninstall.
Optional ACME executable/server and DNS endpoints belong in reviewed root policy;
the basic template grants none of these external integrations.

Source compilation uses another opt-in policy,
[`agent-policy-source-build.json`](examples/agent-policy-source-build.json).
Install it with `--enable-agent --enable-software --enable-source-build` and an
explicit `--agent-policy` path. This prepares the noninteractive
`powerlinux-build` user/group, its private `/var/lib/powerlinux-build` home and
root-owned `/var/cache/powerlinux-build` with mode 0711. Individual build
directories are private to that compiler identity. It must differ from the API,
software runtimes, terminal and scheduled-script profiles by OS identity;
the API cannot select its shell, compiler argv or staging paths.
Only reviewed catalog source recipes are eligible, with pinned artifact hashes.
The installer does not compile software or install compiler dependencies.
The example leaves global system-package installation disabled; dependencies
must already exist or be enabled through separately reviewed package policy.
Existing policies keep source compilation disabled unless explicitly enabled.

Agent state is root-owned/private under `/var/lib/powerlinux-agent`; software
receipts, site keys, system plans and terminal metadata never live beneath the
API-owned data directory. The independent root systemd unit owns
`/run/powerlinux-agent`, and its socket is root:powerlinux 0660. Unix peer UID is
checked in both directions, independently of file permissions. Installation
statically checks the candidate policy without recovering plans or executing
management actions. The source must be an absolute root-owned private file with
protected root-owned directory ancestors, so another UID cannot replace a
reviewed policy through a writable parent. Root-owned sticky `/tmp` permits
private root temporary directories. Group/world-readable policies are rejected.

Privileged changes use typed plans with root-private snapshots, hash comparison,
preflight, real effect verification and failed-change restoration. Connectivity
changes require confirmation before the trusted deadline; otherwise they revert.
An unconfirmed change excludes subsequent host mutations. Rollback refuses to
overwrite later external changes. Protected service profiles come from trusted
policy or root-owned software receipts; arbitrary unit names are never action
inputs. Default core installation changes no SSH/firewall/locale/shell/cron.

Schedulers store named actions in SQLite and recheck the persisted identity's
current scopes/resources before each run. Manual triggering uses the caller's
authority. Private scripts select a trusted shell/UID/work directory profile,
store body in encrypted resource-bound secrets, pin its expected revision and
send the body through private stdin. Root scripts additionally require explicit
root policy, `terminal:root` and host authorization. Task metadata and audit
summaries contain IDs/revisions, never the script body. Script stdout is normal
task output, so a script should avoid deliberately printing sensitive values.

## Update, rollback and uninstall

Repeat installation with the same artifact for an idempotent check, or specify a
new version and hash for update. A version name is immutable: a different artifact
under an existing name is rejected. The service is stopped before data snapshot;
the version link is switched atomically, then the service and health check run.
Production transactions acquire the same `server.lock` after stopping the API
and hold it while copying/restoring data, then release it before service start.
Local `init`/`recover-access` commands cannot mutate the snapshot concurrently.
Production failures restore prior binary, database, API configuration/permissions
and matching unit while preserving failed-version evidence. Root Agent state
is fully snapshotted, but its latest ownership receipts and trusted policy are
preserved: real software installations or completed host recovery cannot be
undone by overwriting bookkeeping with an older snapshot. The selected binary
checks the current policy without running actions; a compatible Agent must pass
a Unix probe as the API UID with exact version/policy hash. An incompatible or
unhealthy Agent remains stopped/disabled with `agent-recovery-required` evidence;
the API rollback completes and prints the recovery requirement.
For a failed upgrade before the candidate Agent was ever attempted, its old
policy/unit can safely be restored. The durable transaction marks an attempt
before starting the Agent, whose constructor can already recover host changes.
After that point failure retains the latest policy/ledger, even if the API UID
cannot reach the Agent; the API can recover while the Agent explicitly requires
operator recovery. Manual rollback always preserves the latest policy/ledger.
The prior unit is restored with its binary, including phase-one releases whose
CLI did not have the new configuration flags. The new API is checked before its
privileged Agent starts. Upgrades preserve existing server configuration and
Agent policy unless a replacement policy was explicitly requested.
A completed snapshot and pending journal allow recovery after a killed installer.
The next operation detects an interrupted transaction, restores it and exits so
the operator can inspect evidence and repeat the requested operation.

```sh
bash scripts/rewrite/install.sh --rollback --prefix /absolute/path/to/powerlinux-test
bash scripts/rewrite/install.sh --uninstall --prefix /absolute/path/to/powerlinux-test
```

Rollback restores pre-upgrade data, so intervening changes will not be active;
they are copied to a retained backup for deliberate recovery. Only one active
rollback target is selected, while earlier snapshots remain on disk. Backups can
be large; inspect disk capacity before an update. No automatic deletion occurs.
Uninstall stops/removes the systemd service and active command link while retaining
data, configuration, snapshots, binaries and the system account. Delete retained
data/account separately only after confirming backup and retention requirements.
Prefix mode creates no user or service; stop its running server before update,
rollback or uninstall. The server's lifetime `server.lock` prevents live mutation.

## Local access recovery

For a forgotten custom login entry, browser entry-gate credentials, CAPTCHA
configuration or maintenance setting, `recover-access` clears those entry
restrictions locally. It acquires the same lifetime data lock as the API and
refuses to run while another process holds it. Stop the API and run as its
ordinary service user so database and encryption-key ownership stay consistent:

```sh
systemctl stop powerlinux.service
runuser -u powerlinux -- /opt/powerlinux/current/folio recover-access \
  --data-dir /var/lib/powerlinux
systemctl start powerlinux.service
/opt/powerlinux/current/folio healthcheck \
  --server-config /etc/powerlinux/server.json \
  --expected-version VERSION_FROM_TRUSTED_RELEASE --timeout 3s
```

Administrator passwords, enrolled MFA, tokens, notes, branding and the API
enabled/disabled setting remain intact. Recovery invalidates browser entry-gate
cookies and does not mint a login session. It requires an initialized
administrator and provides no password or MFA reset. It does not repair listen
addresses, TLS certificates, server configuration or a privileged Agent policy;
inspect their owned configuration and health evidence separately. Prefix users
stop their own process and run the same command with the prefix's private data
directory, without systemd or `runuser`.

When an upgrade or rollback records `/opt/powerlinux/agent-recovery-required`,
keep the Agent stopped until its current policy and root-owned receipts have
been inspected. Check policy compatibility with the selected binary using
`powerlinux agent --policy /etc/powerlinux/agent-policy.json --check-policy`
before any restart. Restoring an old root-state snapshot alone cannot undo a
real software installation, firewall change or host recovery that already ran.
Local browser-access recovery does not clear this Agent recovery requirement.

## Validation scope

`make rewrite-install-test` uses explicitly marked binary fixtures to test real
filesystem changes, checksum rejection, archive safety, repeat installation,
rollback, data retention, lock exclusion and recovery. These tests do not prove
the Go application works or systemd/cloud VM installation passes. Build, real
HTTP/MCP/browser checks, disposable cloud VM installation/upgrade/reboot and
target-architecture execution must be recorded separately. Cross-compilation
does not establish native arm64 execution or Linux distribution compatibility.

`python3 scripts/rewrite/test-package.py /path/to/actual-package.tar.gz` additionally
installs and runs the real binary in a private prefix, validates live HTTP health,
session initialization, embedded Next assets and CSP, rejects a live upgrade,
checks graceful SIGTERM, repeats installation and verifies retained-data uninstall.
This is separate from disposable VM/systemd validation. CI runs it for amd64;
arm64 is cross-compiled until actual target execution is provided.
